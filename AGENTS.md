Salon management SPA (Farsi/RTL, Toman currency, Jalali dates). Next.js 16.3.3 + React 19.2.4 + Tailwind v4.

## Key quirks & gotchas

- **No `tailwind.config.js`** — Tailwind v4 config is CSS-based, all theme tokens in `src/shared/styles/globals.css` within `@theme inline { ... }`. Tokens are referenced as e.g. `bg-surface-tertiary`, `text-content-primary`.
- **`@/*`** maps to `src/*`.
- **`axios-case-converter`** is listed in `package.json` but not referenced anywhere in `src/` — no automatic snake_case↔camelCase conversion (the API already speaks camelCase).
- **Icon library: `@phosphor-icons/react` only.** Don't use `lucide-react` (not installed) or `@radix-ui/react-icons` (still listed in `package.json` but unused — an earlier `Select.tsx` import from it was a bug; don't reintroduce either).
- **`useMediaQuery`** — `src/shared/hooks/useMediaQuery.ts`, exported from the `shared/hooks` barrel.
- **ESLint: effectively disabled** — `eslint.config.mjs` has `nextVitals` and `nextTs` configs commented out.
- **No Storybook `.storybook/` config** — packages installed but not wired up.

## Architecture

The app has three separate surfaces:

```
app/(pages)/layout.tsx              ← Root layout (RTL, Ravi font, Providers)
app/(pages)/(main-pages)/           ← Customer app, wrapped in <Header> + <BottomNavigation>
  (home)/                           ← Public landing page
  profile/ reservation/ search/ favorites/ wallet/ notifications/ subscriptions/ salons/[id]/
app/(pages)/(private-routes)/       ← Salon-owner surface (auth required; `/dashboard` requests carry `X-Salon-Id`)
  onboarding/  dashboard/
app/(pages)/(admin-routes)/admin/   ← Platform-admin surface (separate from the two above)
```

- Route groups: `(pages)`, `(main-pages)`, `(home)`, `(private-routes)`, `(admin-routes)`
- Providers composited via `composeProvider()` in `app/common/providers/Providers.tsx`
- Domain services: singleton class pattern in `services/domains/<domain>/` with React Query hooks in `hooks/` subdir
- Auth: Zustand `useTokenStore`, Axios interceptor injects Bearer token, 401 triggers logout
- `RouteAddress` in `shared/data/routeAddress.ts` — route paths (AUTH, HOME, PROFILE, FAVORITES, SEARCH, RESERVATION, SALONS, WALLET, NOTIFICATIONS, SUBSCRIPTIONS, ONBOARDING, DASHBOARD, …)
- Theme: light/dark switching (Figma-sourced palette). Dark is default — background `#00182f`, primary teal `#4fa39a`; light overrides — background `#ffffff`, primary `#185851`. All tokens in `globals.css` (`@theme` = dark values, `:root[data-theme="light"]` = light overrides, plus a plain `:root { }` block for tokens with no Tailwind-utility usage yet — Tailwind v4 tree-shakes unused `@theme` vars). State: Zustand `useThemeStore` (`services/theme-store/`, persisted to localStorage) + an inline blocking script in `app/layout.tsx` that sets `<html data-theme>` before paint (no FOUC). Toggle lives in Profile → «حساب من» (the «ظاهر» group in `SettingsList.tsx`) and in the panel account sheet.

### Surface boundaries

- **Customer** routes live under `(main-pages)/`. `BottomNavigation` stays customer-only (includes Favorites).
- **Owner** routes live under `(private-routes)/` (`onboarding` and `dashboard`). Chrome (`dashboard/_components`): `PanelHeader` (salon name — tap to switch when there are several; notifications bell with the unread badge from `GET /api/notifications/unread-count`, polled every minute and refreshed by read / read-all; avatar → account sheet with «حساب من», theme, switch salon, customer app, logout-with-confirm) + role-specific nav from `nav.ts` (`getPanelNav`): Owner `نوبت‌ها · مشتریان · ＋ · مالی · سالن`, Staff `نوبت‌ها · مشتریان · ＋ · من`. Mobile uses `PanelBottomNav` (center «＋» opens the single panel `QuickBookDrawer` via `useQuickBookStore`, booking into the day the board shows); `lg+` uses `PanelSideNav`. Only «مالی» has in-section tabs (`PanelSubnav`). Setup pages (staff, services, schedules, salon-info, subscription) are reached from the `/dashboard/salon` hub and show a back arrow (`DashboardPageHeader backHref`); Staff's `/dashboard/me` hub holds own appointments + own schedule + «درآمد من» (`GET /api/staff/me/earnings`: share for این ماه / ماه قبل and own payouts). Dashboard shell is `720px` (sidebar layout up to `1040px` on `lg+`); onboarding stays `600px`.
- **Platform admin** routes live only under `(admin-routes)/admin/` (pending-salon approval, salon suspend/restore, review moderation, reports, subscriptions/billing, users, platform reports) with services in `services/domains/admin`. Never put admin UI or AdminOnly actions in the customer or owner surfaces.

## UI conventions

- Login/OTP always lands customer/global (salon store cleared). Post-login destination: `resolvePostLoginRedirect()` (`redirectUrl` then `?callback=` / session). Use `getLoginHref(returnPath)` for auth CTAs.
- Dashboard with no active salon in this tab: last-used (`lastSalonPublicId`) or single membership → auto-pick; multiple → in-layout «انتخاب سالن». Picking is local (`useSelectPanelSalon`, no API call). Memberships come from `GET /api/auth/me` via `AuthMeMembershipsSyncProvider`. The customer header's `BusinessSwitcher` lists salons as «ورود به پنل سالن» (hidden when there are no memberships) — there is no context switcher.
- Home header: guests see «ورود»; `BusinessSwitcher` only when logged in (role via `salonRoleLabel`, logout confirms).
- Customer profile: the menu's «حساب من» (`/profile/settings`) holds name (→ edit), mobile (read-only, change via support), «امنیت و رمز عبور», theme and «خروج از حساب» (confirm dialog). Owners of an approved salon see «پنل سالن» instead of the registration/subscription rows.
- Owner dashboard pages: `/dashboard/catalog`, `staff` + `staff/[staffPublicId]`, `schedules`, `salon/info` · `salon/photos` · `salon/branches` (salon profile edit; `/dashboard/salon-info` only redirects to the hub; `/onboarding` remains create/resume-draft only), `finance`, `reports` («گزارش عملکرد»; `z-report` → finance and `analytics` → reports only redirect), `payouts` («تسویه پرسنل»), `notifications`, `my-appointments` («نوبت‌های من» as staff, both roles), `customers` + `customers/[customerPublicId]` («رزروهای مشتری», both roles), `staff/[staffPublicId]` (one person, SalonOwner only: tabs «نوبت‌ها» (`appointments/staff/{publicId}` history) · «برنامه» · «خدمات و قیمت»; «⋯» → change branch / remove with confirm). The standalone staff-services and per-staff appointments pages are gone — per-person price/duration lives only in that tab (`StaffServicesTab`: catalog staff-services when the numeric `staffMemberId` is known, else roster `offeringPublicIds`). Nav items match sub-routes by prefix (`isPanelNavItemActive`). Owner-only pages (reports, finance, catalog, staff, staff-services, salon-info, the salon hub) are wrapped in `<OwnerOnly>` in their `page.tsx` — Staff gets a notice instead of actions the backend rejects; finer checks use `useIsSalonStaff()`. Show role names via `salonRoleLabel()` (never raw `SalonOwner`/`Staff`). Panel wording: «خدمات» (not «کاتالوگ»), «صندوق روز» (not «Z-Report»).
- Customer pages: `/wallet` must render real balance/transactions; `/notifications`; `/favorites` plus a heart toggle on catalog/search/detail cards (`salonPublicId` Guid).
- Subscription operational lock: dashboard banner + quick-book disabled when `GET /api/subscriptions/me/entitlement` has `isEntitled=false`. Online booking maps `errors.field=subscription` to a customer-facing lock message. Cancel/complete stay unlocked.
- Shared owner UI lives in `dashboard/_components/` (`DashboardPage`, `DashboardCard`, `DashboardSelect`, `DashboardDateField`, empty/skeleton/toast). Do not use the broken shared `Select.tsx` in the dashboard.
- Theme tokens: prefer `bg-surface`, `bg-input` / `border-input-border` / `text-foreground` / `text-foreground-muted` for new UI. Legacy aliases (`surface-tertiary`, `content-primary`, `border-primary`, …) are defined in `@theme` and may stay in existing primitives. Photo overlays use `text-on-media` / `bg-overlay`. Hover/highlight backgrounds (`surface-hover`, `input-hover`, `accent`) are a subtle `color-mix` of surface + primary so `text-foreground` stays readable in both themes — never set them to a strong/inverted color. Do not hardcode `bg-black`, `text-white`, or hex colors in classNames.
- All times and dates are Asia/Tehran everywhere (display, "today", calendar math, payloads) — never the device timezone. Use `shared/utils/salonTime.ts`: `formatSalonDateTime`/`formatSalonDate`/`formatSalonTime` (instead of `toLocale*String`), `utcToSalonTime`, `utcToSalonYmd`, `salonTodayYmd`, `addDaysYmd`, `ymdToDate` (date-only strings), `salonClockParts`, `salonWeekday`, and `salonWallClockToUtcIso` for any salon wall-clock value sent to the API. Don't call `Date` getters (`getHours`, `getDate`, `getDay`…) on API instants or build "today" from them.
- Digits are English (Latin) everywhere in the UI. Every Intl / `toLocale*` call uses `APP_LOCALE` (`shared/utils/locale.ts` = `fa-IR-u-nu-latn`: Persian words + Jalali calendar, Latin digits) — never bare `"fa-IR"`; don't hardcode Persian digits (۰–۹) in UI text. The Ravi font draws Latin digits as Persian glyphs, so `globals.css` maps U+0030–0039 to a system-font `latin-digits` face placed before Ravi — keep it first in the font stack.
- Money = Toman; dates = Jalali in UI, `yyyy-MM-dd` / ISO toward the API. Every money input uses `MoneyInput` (`shared/components/primitives/input/MoneyInput.tsx`: `,` thousands separators while typing, «تومان» suffix, numeric keypad, reports a plain Toman number) — never a raw `type="number"` field; money display uses `formatToman`. Every service-duration input (service, pricing rule, per-staff custom) uses `DurationPicker` (`shared/components/primitives/input/DurationPicker.tsx`: 15-minute steps, 15 min–12 h, −/+ and presets, `optional` adds «پیش‌فرض خدمت» = null) and saves are guarded with `isValidServiceDuration` (`shared/utils/serviceDuration.ts`) — durations must be multiples of 15 and at most 720 (backend 400s otherwise). Every phone input uses `PhoneInput` (`kind="mobile"` 11 digits / `"landline"`), or for react-hook-form fields `PHONE_INPUT_ATTRS` + `transformValue={normalizePhoneInput}` (`shared/utils/phoneInput.ts`): tel keypad, LTR digits, Persian/Arabic digits → Latin (backend validates `^09\d{9}$`).
- New-password fields (register set-password, reset-password, change-password) validate with `newPasswordField` and show the live `PasswordRequirements` checklist under the field — both driven by `PASSWORD_RULES` in `shared/utils/passwordRules.ts`, which mirrors the backend (8–72 chars, upper, lower, digit, symbol). Change the rules there only.
- First sign-up (`/auth/register/set-password`, right after OTP) also asks «نام» and «نام خانوادگی» (required, ≤ 100 chars) and sends them as `firstName` / `lastName` in the same `set-password` call, then refreshes `/api/auth/me`.
- Change password (`set-password` with `oldPassword`) signs out every session, this one included: immediately `login-password` with the phone from `GET /api/auth/me` (the JWT has no phone) + the new password and store the new tokens. First-time set (after OTP, no `oldPassword`) keeps the session. 5 wrong current passwords → 429 for 30 min: show the lock message + a link to SMS-code reset.
- Do not ship mock identity, fake businesses, or crypto-style wallet placeholders when wiring real APIs.

## Service type icons

Every `ServiceType` (seeded on the backend — `SalonFlowDbContext.SeedData`) gets a matching icon shown as a themed circular badge (category rows, etc.). The mapping lives in `src/shared/data/serviceTypeIcons.ts`:

```ts
export const SERVICE_TYPE_ICONS: Record<string, Icon> = {
  "کوتاهی مو": ScissorsIcon,
  // ...
};
export function getServiceTypeIcon(name: string): Icon { ... }
```

- **Keyed by the exact Persian `Name` string**, not by id — the API (`ServiceTypeResponseDto.Id`) returns a `Guid` (the row's `PublicId`), not a stable small integer, so the name is the only convenient stable key. Must match the backend seed string byte-for-byte (including any ZWNJ/half-space characters).
- **Icons come from `@phosphor-icons/react`.** Always import the `...Icon`-suffixed named export (e.g. `ScissorsIcon`), never the deprecated bare name (`Scissors`) — check `node_modules/@phosphor-icons/react/dist/csr/<Name>.d.ts` if unsure whether an icon exists before importing it.
- **Unmapped service types** (e.g. a salon's own custom one) fall back to `DEFAULT_SERVICE_TYPE_ICON` (currently `SparkleIcon`) via `getServiceTypeIcon()` — never index the record directly.
- **Rendering pattern** — a circular badge sized `h-[68px] w-[68px]` (adjust to context) with `bg-surface-brand text-content-brand`, icon at roughly 40% of the badge size with `weight="duotone"`. These two classes are derived from `--color-primary`, so the badge recolors automatically between light/dark — never hardcode a color here. See `SearchCategories.tsx` for the reference implementation.

**To add a new service type's icon:** add one entry to `SERVICE_TYPE_ICONS` with the exact seeded Persian name and a semantically fitting Phosphor icon (verify the `...Icon` export exists first), following the same `bg-surface-brand`/`text-content-brand` badge pattern anywhere it's rendered.

## Services & API

- **Contract source of truth:** the backend's OpenAPI snapshot at `D:\SourceSalon\docs\openapi\v1.json`. It is large (~540KB) — to see what changed, use `git -C D:\SourceSalon log -p -- docs/openapi/v1.json` instead of reading it whole. Successful responses with a body are wrapped as `{ "data": ... }`, which the snapshot does not show.
- Singleton domain services in `src/services/domains/<domain>/`; React Query hooks in `hooks/`. Shared domain enums live in `src/services/common/enums/domain-enums.ts`.
- Paths only via `API_ADDRESS` in `src/services/common/apiAddress.ts`.
- Success with body: unwrap `TResponse<T>.data`. Success 204 / empty 200: no `data` expected.
- Auth header: Bearer access token. On 401 with a prior token, refresh via bare axios (not `axiosInstance`) then retry; body is `{ refreshToken }` only (tokens never carry salon context). Failed refresh with inactive membership → 401, force logout, login banner «عضویت سالن دیگر فعال نیست».
- Forgot password (3 steps, all `skipAuthRetry`): `POST forget-password { phone }` (always 200, show no "code sent" text) → `POST verify-reset-code { phone, code }` → `{ resetToken, expiresAt }` → `POST reset-password { resetToken, newPassword }` → `AuthResponse` (logs in). Phone + reset token live only in memory (`useResetPasswordStore`) — never in the URL or localStorage; refresh restarts from the phone step. Show the server `message` on 401; a 401 on reset-password means "get a new code".
- Salon public link (username): every salon has a unique `username`; the share link / QR is always `/s/{username}` (`RouteAddress.SALONS.BY_USERNAME`, helpers in `shared/utils/salonShareLink.ts`), never the Guid. Username is only for that URL — APIs, booking and internal routes keep `publicId`. Set via `save-basic-info` (`username`; required on create, empty on edit = keep current) with `SalonUsernameField` (lowercases, previews link, debounced `GET username-availability`, pass `salonPublicId` when editing); show server 400 `field=username` under the field. After approval a salon can change its username at most 2 times (free before approval), and an old username stops working: `/s/[username]` resolves only the current one via `GET by-username` (404 → «سالن پیدا نشد», no redirect) and has server `generateMetadata` for link previews. The edit page shows that rule next to the field. Read `username` fresh from API responses; never cache it or hardcode the reserved-word list. Owner card with copy/share/QR: `SalonLinkCard` (qrcode.react) — opened from the QR button of the identity card on `/dashboard/salon`.
- `GET /api/auth/me` returns profile plus `memberships` (`salonId`, `salonPublicId`, `salonName`, `roleId`, `roleName`, `branchId`, `branchPublicId`). A salon can appear twice (Owner + Staff): `mapAuthMeMembershipsToSalon` keeps one entry per `salonPublicId` (owner role wins, salon-wide row wins over a branch row). Client syncs them into `useSalonContextStore` via `setMemberships` (`useSyncMembershipsFromAuthMe`); do not set the active salon from `/me` alone.
- Salon context (backend ADR-0012): `switch-context` is gone and tokens are never swapped. The axios request interceptor adds `X-Salon-Id: {salonPublicId}` (+ `X-Branch-Id: {branchPublicId}` only for a branch-scoped membership) **only when the page is under `/dashboard`** (`isSalonPanelPath`); customer, onboarding and admin requests never carry it — customer endpoints answer 403 with it. Opt out per request with `skipSalonContext`. The active panel salon is per tab (sessionStorage); memberships and `lastSalonPublicId` are shared (localStorage). A 403 on a request with the header re-reads `/me` (without the header): if the active salon/branch is gone → clear the panel context and go to `/`; otherwise it is a normal role 403. Switching to a different salon clears the React Query cache.
- ID mapping: public browse Guids ≠ long IDs for salon-owner create/finance. Customer `POST /api/booking/create` body is Guid-first: `{ salonPublicId, branchPublicId?, startTime, notes?, services: [{ offeringPublicId, staffPublicId }] }`. Salon-side quick booking (`POST /api/appointments/quick-book`: phone/fullName/branch/startTime/services) keeps `offeringId` and `staffId` numeric. Salon-side `POST /api/appointments` identifies the customer by `customerCode` (Guid from `CustomerDto` / quick-book result, valid only in that salon) — `customerId` is deprecated.
- Favorites (`CustomerOnly`): `POST/DELETE /api/favorites/{salonPublicId}` with catalog Guid (`SalonCardDto.id`); match heart state via `FavoriteSalonDto.salonPublicId` and `useFavoriteIdsStore` (survives a query clear). `GET /api/favorites` returns card fields (`imageUrl`, `city`, `averageRating`) and only Approved salons. DELETE is always 204 (idempotent). Optimistic toggle; surface mutation errors on the heart.
- Online booking wizard (`/salons/[id]/book`, 5 steps): 1 services (branch picker on the same step only for multi-branch salons) → 2 staff from `GET staff-profiles/by-salon/{id}/for-services` or «اولین نوبت» (`GET /api/booking/first-available` once → prefills date/time/staff; on error/404 fall back to all staff's slots and take staff from the picked slot) → 3 dates (`available-dates` with `offeringPublicIds[]` — never `serviceTypePublicId` alone — plus `staffPublicId` when known) with that day's `GET /api/booking/slots` underneath → 4 `calculate-price` with the resolved staff → 5 confirm + `POST /api/booking/create`. first-available 404 = «نوبت آزادی پیدا نشد», user must pick staff; create failure (except subscription lock) → server message, back to step 3 with the time cleared. Dates/slots/first-available are never cached (`staleTime`/`gcTime` 0, enabled only on their own step). Slot times are Asia/Tehran, never the device zone: `shared/utils/salonTime.ts` (`utcToSalonTime`, `salonWallClockToUtcIso`, used by `toBookingStartTime`). Draft in sessionStorage (`bookDraft.ts`, bump `DRAFT_VERSION` when steps change).
- Customer appointments: `GET /api/appointments/me`, `GET .../me/{id}`, `POST .../{id}/cancel` (Scheduled only). UI under `/reservation` and `/reservation/[id]`. `me` is customer-only — never call it from `/dashboard` (the header makes it 403).
- Appointment history (all paged `TPagedResult<IAppointmentHistoryItem>`, query `from`/`to` `yyyy-MM-dd` Tehran-inclusive, `status`, `page`, `pageSize` ≤ 100): `GET /api/appointments/me` (any logged-in user), `.../staff/me` (panel, Staff/Owner), `.../customer/{customerPublicId}` (panel, Owner/Staff; Guid from `CustomerDto.publicId`), `.../staff/{staffPublicId}` (panel, Owner only). Hooks in `useQueryAppointmentHistory.ts`; shared UI `AppointmentHistoryPanel` (filters + list + paging).
- Reviews: create/edit/delete + public list by numeric `salonId`. Track customer submission via `useMyReviewsStore` + `GET /api/reviews/{id}` for pending badge. Salon reports: `POST /api/salon-reports`. In the public list the author is only a first name or «کاربر صفا» and `customerId` / `appointmentId` / `responderUserId` are 0/empty — never rely on them.
- Subscription money is in RIALS in the API (plans, `campaignPrice`, discount `finalPrice`, checkout/preview, platform invoices, promo fixed amounts, platform reports) — the UI is Toman: display via `formatRialAsToman`, send admin-typed amounts via `tomanToRial` (`subscriptions/utils/subscription-display.ts`). Never compute a discounted price client-side; show `campaignPrice`/`finalPrice`. The old `api/subscriptions/campaigns` endpoints are gone. Admin plan management (`/admin/subscriptions` «طرح‌ها» tab): `api/admin/subscription-plans` list/create/`PUT {planPublicId}`/`activate`/`deactivate` (no delete — deactivate keeps subscriber history; warn with `activeSubscriberCount`) and one percentage discount per plan via `PUT/DELETE .../discount` (`durationDays` omitted = no end, `startsAt` omitted = now). Public `GET /api/subscriptions/plans` returns active plans with `discountPercent`/`discountRemainingDays`; show original price struck through + `campaignPrice` + «X٪ تخفیف {name} — N روز باقی مانده».
- Subscriptions: plans/me/entitlement/trial/checkout. Gate salon create with `useSubscriptionEntitlement().canCreateSalon` (entitled && under maxSalons). Gate owner appointment create / quick-book with `isEntitled`; map API `errors.field=subscription` (400) to lock copy + `/subscriptions` CTA. Checkout creates a Pending platform invoice (no PSP yet).
- Onboarding: `/onboarding` — 7-step save-* + submit-for-review; draft in `useOnboardingDraftStore` (salonPublicId). New create blocked without entitlement; resume draft allowed.
- Owner salon profile edit — three pages under the «سالن» hub: «اطلاعات و تماس» (`/dashboard/salon/info`, one form + sticky `SaveBar` while dirty), «عکس‌ها» (`/dashboard/salon/photos`, every upload/delete saves at once and every delete confirms), «شعبه‌ها» (`/dashboard/salon/branches`, list → one-branch sheet; save/remove write the whole list via save-branches; remove confirms). Section components and mappers stay in `dashboard/salon-info/components` + `utils`. hydrate via `useQuerySalonById`; panel edits go through `services/domains/salon-panel` (active salon from `X-Salon-Id`): Basic+Contact via `PATCH /api/salon/profile` with only the changed fields (`""` clears an optional one; `GET /api/salon/profile` gives `usernameChangesLeft` for the username note); branches one at a time via `POST /api/salon/branches`, `PATCH` / `DELETE /api/salon/branches/{publicId}` — the remove dialog first reads `.../removal-impact` and blocks removal while it has future appointments, staff or is the last active branch (an unfinished onboarding draft of the same salon gets its branch list synced); gallery order via `PUT /api/salon/media/gallery/order` (arrows on each picture, all gallery publicIds once). Data comes only from `useQueryAgenda` (`appointments/hooks`) = one `GET /api/appointments/agenda` call (`from`/`to` ≤ 14 days, `staffPublicId`, `branchPublicId`). Status labels (`appointmentStatusLabel`): رزرو شده · در سالن · انجام شد · لغو شد · مراجعه نکرد (never «عدم حضور» / «نیامد»). Lifecycle calls are `check-in`, `complete`, `no-show`, `cancel`, `reschedule`; their mutations invalidate the day list, day-board and `staff/me` keys.
- «نوبت جدید» (`QuickBookDrawer`, one instance in the layout, opened by the nav «＋»): customer search by name or phone (`GET /api/customers`) or «مشتری جدید با {phone}» → one or more services → staff who do all of them (`for-services` with `matchAll`) → branch (multi-branch only) → day + 15-min time (`DayPicker` / `TimePicker` in `_agenda/DayTimePicker.tsx`, shared with reschedule) with a staff-conflict warning. Always books via quick-book (find-or-create by phone), one `{ offeringId, staffId }` per service; success is a toast, never a «#id» dialog. Salon-side cancel / reschedule / no-show each confirm in a dialog with `NotifyCustomerCheckbox` («اطلاع به مشتری با پیامک») sent as `notifyCustomer` — default on for cancel and reschedule, off for no-show; never shown on the customer's own cancel. A salon-side cancel refunds a wallet-paid deposit to the customer's wallet (only the customer's own late cancel forfeits it); a cash/card deposit is returned by the salon itself.
- Pages opened from SMS links (`/reservation`, `/wallet`, `/dashboard/*`, `/onboarding`, …) must send a guest to login and back to the exact same path: use `useRequireLogin` (`shared/hooks`) — it waits for the persisted token store to hydrate before redirecting — or `getLoginHref(pathname)`.
- `GET /api/customers` (search, `segment` all/new/inactive, `sort`, pagination; rows carry `visitsCount`, `lastVisitAt`, `nextAppointmentAt`, `noShowCount`) backs `/dashboard/customers` (segment chips همه / جدید / بدون مراجعه‌ی اخیر). The customer page (`/dashboard/customers/[customerPublicId]`) reads `GET /api/customers/{publicId}` (`useQueryCustomerDetails`: name, phone, stats, salon note, upcoming as agenda rows) and shows «تماس / پیامک / نوبت جدید» (quick-book opened with the customer pre-picked via `openQuickBook({ customer })`), the editable salon note (`PATCH` `{ note }`), upcoming appointments and month-grouped history (`AgendaRow variant="history"`; tap → `AppointmentDetailsSheet`). `useCustomerPreviewStore` (in memory, never in the URL) only fills the header until details load.
- Catalog owner module uses `api/catalog` as source of truth (replaces legacy `api/salon-offering` for dashboard operations): offerings CRUD, `PATCH .../active`, staff-centric `GET/PUT /api/catalog/staff/{staffMemberId}/services`, offering-centric `GET/POST /api/catalog/offerings/{id}/staff` (POST upserts the person's price/duration) + `DELETE .../staff/{staffMemberId}`, and pricing-rules CRUD. «خدمات» page (`/dashboard/catalog`): list (icon, duration · price · N people, inactive last) → `ServiceEditor` sheet: price / duration / deposit / «قابل رزرو», «بیشتر» (color, branch), «چه کسانی انجام می‌دهند» (instant toggles, per-person price/duration), «قیمت ویژه» (pricing rules scoped to a branch or a date range only — staff-specific rules are not offered; per-person price lives on the assignment). After create the same sheet continues with providers. Deleting a service or a special price confirms. Any assignment change invalidates staff-services, offering-staff, for-services and roster keys. «برنامه‌ی تیم» (`/dashboard/schedules` for the owner, `TeamSchedule`): 7 day chips, each person's hours/off/leave that day, tap → their page.
- Staff schedules use `api/working-schedules` (weekly) and `api/special-schedules` (specific date overrides/off days). Staff may edit only their own schedule (403 otherwise → «فقط برنامه‌ی کاری خودتان…») but may view colleagues' schedules. `useMyStaffMember` (`dashboard/_staff`) = `GET /api/staff/me` (404 → not staff here). API day numbering is 0 = Saturday … 6 = Friday (backend `SalonWeek`). Editors (`dashboard/_schedule`, both need `staffMemberId` + `staffPublicId`): `WeeklyScheduleEditor` (reads `working-schedules`, one row per day, optional break = split shift, edited in a sheet, saved in one `PUT /api/staff/{publicId}/schedule/weekly` with `ranges`) and `SpecialDaysEditor` (upcoming exceptions; new leave / special hours for one day or a range ≤ 62 days = one `POST /api/staff/{publicId}/schedule/exceptions`; edit/delete of a single day stays on `special-schedules`; delete confirms). Both show the appointments the change leaves outside the shift (`ScheduleConflicts`) — never cancelled. «برنامه‌ی تیم» reads `GET /api/schedules/team`. Staff management (owner, `services/domains/staff`): `useSalonStaff` = `GET /api/staff` (names, ids, branch, invitation state, today's hours) + the onboarding roster only for each person's `offeringPublicIds`; invite `POST /api/staff/invitations` (returns `staffMemberId` at once), change branch `PATCH /api/staff/{publicId}`, remove `DELETE` after `GET .../removal-impact` (the dialog says how many future appointments get cancelled and SMSed), «ارسال دوباره‌ی دعوت» `POST .../resend-invitation` for pending invitations. Invoice add/delete item, invoice cancel, payment refund and customer delete are owner-only (403 for Staff; no UI for them today — keep them out of Staff views).
- Wallet = platform credit, currently disabled on the backend (`Wallet:Enabled=false`, not exposed to the client): only `GET /api/wallets/me` and `.../me/transactions` exist — salons have no wallet lookup/charge/debit endpoints and can't record a Wallet payment (400 `field=paymentMethod`), so the owner finance page offers no wallet card and no Wallet payment method. Booking deposits aren't taken online: `calculate-price` returns `amountDueNow=0` — show «بیعانه در سالن پرداخت می‌شود» from `totalDepositAmount` instead of an online-deposit box.
- Finance: `api/invoices`, `api/payments`, `api/tips`, `api/reports/z-report` (include `transferTotal` / `walletTotal` / `collectedTotal`). Always send a unique `idempotencyKey` on payment create. Money is collected from the appointment itself (owner only — Staff never see money): «انجام شد و دریافت» in `AppointmentDetailsSheet` opens `CheckoutStep` = one `POST /api/appointments/{publicId}/checkout` (`completeFirst`, payments, optional tip and owner discount, `idempotencyKey`); `PaymentStep` stays for the finance page (amount prefilled with the outstanding/total, methods نقد / کارت / انتقال only — no online gateway, Wallet disabled); the invoice is issued behind the scenes on the first payment (`POST /api/invoices/from-appointment/{appointmentId}` — only once per appointment, so look the invoice up first: recent `GET /api/invoices` matched by `appointmentId`). A completed appointment shows «دریافت X تومان» or «پرداخت شد». Payments invalidate invoices, z-report, dashboard summary and report keys. «مالی» (`/dashboard/finance`): period chips (امروز / دیروز / این هفته = since Saturday / این ماه = Jalali month — `_components/periods.ts`), «صندوق روز» (z-report) for one day or revenue-by-method for a range, «دریافت‌ها» (`GET /api/payments` for the period: customer · method · time · amount, refunds marked; keyed under the reports key so money mutations refresh it), «پرداخت‌نشده» (Issued + PartiallyPaid invoices shown by `customerName` and appointment time; tap → `PaymentStep` in a sheet), links to «تسویه پرسنل» and «گزارش عملکرد». `/dashboard/z-report` redirects to it. Never show «Z-Report» or invoice internals as the primary concept. Customer wallet UI uses the real `me` wallet endpoints (balance + transactions) and says top-up/payment is not active yet.
- Owner reports: `GET /api/reports/dashboard-summary` plus revenue/outstanding/funnel/staff-performance/peak-hours/fill-rate/customers/* and `GET /api/reports/export` (CSV blob, unwrap is the file). Query `from`/`to` as `yyyy-MM-dd`; optional `branchId`. One page «گزارش عملکرد» (`/dashboard/reports`): period chips (این هفته / این ماه / ماه قبل / بازه‌ی دلخواه), branch chips when multi-branch, four headline numbers with % change (درآمد, نوبت انجام‌شده, مشتری جدید from `GET /api/reports/overview` against the previous period; مراجعه‌نکرده and the sparkline from dashboard-summary), then topic tabs درآمد · نوبت‌ها · مشتریان · خدمات · پرسنل as ranked bar rows (`BarRow`) — no accordions, no chart grids; each tab fetches only while open; export lives behind the download icon. `formatMoneyOrDash` already appends «تومان».
- Owner ops: payouts/earnings (`api/earnings`, `api/payouts`), commission plans (`api/commission/plans*`), notifications inbox (`api/notifications`). «تسویه پرسنل» (`/dashboard/payouts`): per person from `GET /api/payouts/overview` (این ماه / ماه قبل: share, work done, ready-to-pay, waiting count, last payout) with «تأیید همه» (pending earnings by id) / «ثبت تسویه» (period sheet → `GET /api/payouts/preview` amount → `POST /api/payouts` with the preview's `periodStart`/`periodEnd` and `approve: true`), payouts Approved → «پرداخت شد» (method + confirm; an old Draft still offers «تأیید»), and «طرح کمیسیون» (`CommissionPlans`): a real form — plan name/active, rules per scope (همه / یک خدمت by numeric `serviceTypeId` / یک نفر), percentage 0–100 or fixed Toman, «شامل انعام»; deletes confirm. Never a raw-JSON editor.
